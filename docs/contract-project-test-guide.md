# Contract / Project Phase B.1 — Docker Test Guide

> **Scope**: step-by-step test instructions for Phase B.1 of [docs/internal-contract-project-relationship.md](internal-contract-project-relationship.md) (PR #13, commits `7b5154a9` B.1a + `fe88596a8` B.1b on `claude/repo-code-summary-22f444`).
>
> **Audience**: anyone running tests in the independent Docker test environment. This development machine does **not** run `pnpm dev` / `pytest` / `pnpm install`; verification lives elsewhere.
>
> All commands assume your shell is at the repo root unless a path is given explicitly.

## 0. Pre-flight

### 0.1 Tools needed

- `docker` (>= 24) and `docker compose` (v2 — the `docker compose` CLI, not the old `docker-compose`)
- A checkout of this repo at the `claude/repo-code-summary-22f444` branch
- The standard env file generated by `setup.sh` (see AGENTS.md "Backend tests (Docker)")

### 0.2 Pull the right branch

```bash
git fetch origin
git checkout claude/repo-code-summary-22f444
git log --oneline -5
# expected top: fe88596a8 feat(web): add Contract / ContractProject types + service + store + project-info block (Phase B.1b)
```

### 0.3 Bring up the stack

```bash

```


The plan must list the Phase A migrations (`0126_internal_contract_project` and `0127_internal_contract_project_is_unique_key_reset`) as already-applied-or-to-apply. If they are missing from the plan, the checkout is on the wrong branch.

```bash
docker compose -f docker-compose-test.yml run --rm api-tests pytest \
```

## 2. Backend integration test (real spreadsheet)

The import command (Phase A's `import_historical_project_data`) is the only writer of Contract / ContractProject rows today. Running a real dry-run against `项目汇总表.xlsx` is the end-to-end proof that Phase A and Phase B.1a's read API agree on the data.

### 2.1 Prepare a real spreadsheet

The independent test environment should have a copy of `项目汇总表.xlsx`. Copy it into the API container's `/code/` (or any path readable by the `api` service):

```bash
docker cp /path/to/项目汇总表.xlsx plane-api-1:/code/project_summary.xlsx
```

(The container name `plane-api-1` is the Compose default; `docker compose -f docker-compose-local.yml ps` will confirm it.)

### 2.2 Pick a workspace and operator

You need a workspace slug and a workspace-member email to attribute the import to. The test workspace created by the seed fixture (`WorkspaceFactory` etc.) is fine:

```bash
docker compose -f docker-compose-local.yml exec api \
    python manage.py shell -c "
from plane.db.models import Workspace, WorkspaceMember
print(Workspace.objects.first().slug)
print(WorkspaceMember.objects.filter(is_active=True).first().member.email)
"
```

### 2.3 Run the import dry-run

```bash
docker compose -f docker-compose-local.yml exec api \
    python manage.py import_historical_project_data \
        /code/project_summary.xlsx \
        --workspace <workspace-slug> \
        --created-by <member-email> \
        --dry-run
```

Expected:
- `Created N project(s)` where N is the number of valid rows in your xlsx (typically 150-180 for the real `项目汇总表.xlsx`).
- Warning count depends on data quality; the previously-tuned baseline is 6 warnings, all from intentionally-untouched multi-value dropdown cells per `docs/internal-project-custom-fields.md`. The new column-A-ignore change must not add to that count.
- A summary line listing `Skipped: X blank, Y missing unique key, Z duplicate, W error. V field-level warning(s) (see above).`

If you instead see the new `--dry-run` introducing new warnings, file a regression — Phase A's data-quality invariants (A column ignored, F column datetime/int reverse-parsed, M column as new unique key) are the contract PR #13 relies on.

### 2.4 Confirm the read API sees the imported rows

```bash
# inside the container:
docker compose -f docker-compose-local.yml exec api \
    python manage.py shell -c "
from plane.db.models import Contract, ContractProject
print('contracts:', Contract.objects.count())
print('links:', ContractProject.objects.count())
"
```

Then exercise the new endpoints:

```bash
# Get a session token or use Basic auth as configured for the test env.
# Workspace contract list (B.1a):
curl -s -H 'Cookie: <session>' http://localhost:8000/api/workspaces/<slug>/contracts/ | jq '.[0]'

# Per-project links (B.1a):
curl -s -H 'Cookie: <session>' \
    http://localhost:8000/api/workspaces/<slug>/projects/<project-id>/contracts/ | jq '.[0]'
```

The first response must include `project_links: []` or `project_links: [{...}]` depending on whether the contract was linked to a project during the import.

## 3. Frontend test (browser smoke)

The frontend changes are read-only and concentrated on the project-info page. There is no new interactive state.

### 3.1 Install + dev server

```bash
cd apps/web
pnpm install
pnpm dev   # serves on http://localhost:3000 by default
```

(If you also run the admin app, the same dev script covers it on port 3001. The contract block lives only in `web`.)

### 3.2 Visit the project-info page

1. Log in as a workspace member with at least MEMBER role.
2. Navigate to `/<workspace-slug>/projects/<project-id>/project-info/`.
3. Confirm the page renders the existing 17 custom-field groups (this is the no-regression check — Phase A's `DEFAULT_PROJECT_CUSTOM_FIELDS = 17` is the source of truth).
4. Scroll past the last field group. The new "Related contracts" (en) / "关联合同" (zh-CN) section must appear below the groups.

### 3.3 Three states to verify

Pick a project you imported in step 2.3 and walk through these three states on it:

**State A — populated (most projects imported in step 2.3)**

- A `<ul>` of contracts is shown, one per row.
- Each row shows `contract_no`, optionally `contract_name`, and below that a separator-joined summary of `customer`, `sign_date`, and `total_amount` (formatted as `${total_amount} 万元`).
- A right-aligned `allocation_ratio %` appears if the import command wrote one (the import writes a 0-1 value; the block formats it as a percentage assuming a `%` suffix already exists in the serializer output; check `apps/api/plane/app/serializers/contract.py` `ContractProjectSerializer.allocation_ratio` if the displayed value looks wrong).
- Clicking a row does **nothing** (no link target) — that's intentional; the contract detail page is Phase B.2.

**State B — empty**

Pick a project that was NOT imported in step 2.3 (or one whose ContractProject rows were all skipped) and visit the same URL. The block shows the empty state string from `project_custom_field.settings.project_info_page.related_contracts.empty` ("No contracts are linked to this project yet." / "该项目暂未关联合同。").

**State C — loading**

Throttle the network in DevTools to "Slow 3G" and hard-reload. The block shows the `<Loader>` skeleton (two grey bars) until both fetches resolve.

### 3.4 Console / network checks

- Network tab: two `GET` calls fire on first project-info visit:
  - `/api/workspaces/<slug>/contracts/` -> 200 with the full workspace list
  - `/api/workspaces/<slug>/projects/<id>/contracts/` -> 200 with the per-project link list
  - No 4xx, no repeated calls (the store dedupes on `contractsFetched` / `linksFetched`).
- Console: no MobX warnings. If `useStrictMode` triggers, the most common cause is a render-time call to `getContractsForProject` before the useEffect fires; reload the page and confirm the issue is gone (the effect uses `void` to mark the fetches as fire-and-forget intentionally).
- React DevTools: `RelatedContractsBlock` is the last child of the `<div className="mx-auto flex max-w-5xl flex-col gap-8">` container; if it shows up between field groups, the integration site is wrong.

### 3.5 Logout smoke

Log out from the workspace. The `resetOnSignOut` path on `CoreRootStore` should re-instantiate the contract store; the next login on any workspace must not see stale contracts from the previous session (verified by visiting project-info immediately after re-login and seeing the loader, then the new workspace's contracts within ~100ms).

## 4. Known gaps and out-of-scope items

These are **intentionally not in Phase B.1** and should not be flagged as regressions:

- No mutating Contract / ContractProject endpoints (B.2). The import command is still the only writer.
- No per-row link target on the related-contracts rows (B.2).
- No contract detail page (B.2).
- No contract list / search / filter page (B.2).
- No ContractProject management UI (B.3).
- No allocation_ratio>1 guard is tested on the frontend; the backend serializer rejects the value with `ALLOCATION_RATIO_OUT_OF_RANGE` (see `apps/api/plane/app/serializers/contract.py`), and the frontend displays whatever the backend returns. If you see a value > 1 in the UI, file a backend regression.
- No matrix view (Phase D) and no relationship graph (Phase E).

## 5. Rollback

If Phase B.1 needs to be reverted:

```bash
git revert <merge-commit>        # replace with the actual SHA from the PR
docker compose -f docker-compose-local.yml exec api python manage.py migrate <prev> <next>
```

The backend routes simply unregister; the frontend block disappears on next rebuild. No data migration was added in PR #13 (Phase A's `0126` and `0127` are already merged), so no historical data needs cleanup.

If the revert is the result of a Phase B.1a issue (B.1b depends on B.1a being live), revert the entire PR rather than trying to split — the frontend block's empty/error states are only meaningful when the backend routes work.
